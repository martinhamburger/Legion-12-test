# 十二军团策略优化系统：实施规划

## 1. 目标

系统要同时回答四类问题：

1. **配什么卡**：40–50 张卡如何选择，核心卡、通用卡、过牌、解场、士气修补和天灾保险如何分配。
2. **什么时候打什么**：起手换牌、每个士气阶段的行动顺序、优势/均势/劣势局决策。
3. **为什么这样做**：说明组合概率、士气利用、局面价值、风险和反事实方案。
4. **结论是否可靠**：交换先后手、不同抽牌与天灾、不同对手策略下是否仍然有效。

第一版不追求一次实现全部阵营。最快且最可靠的路线是：**选定两个阵营，只实现相关卡牌和对局，再逐步扩展。**

## 2. 避免“笨策略”的总原则

### 2.1 不从随机策略开始

纯随机自对弈会把大量计算浪费在明显错误的动作上。第一版策略由四层组成：

```text
合法动作过滤
→ 战术安全规则（斩杀、防斩杀、关键阈值）
→ 人类策略融合后的行动评分
→ 束搜索 / Monte Carlo rollout 做局部校正
```

强化学习放在最后，只学习“强基线仍然做不好的部分”。

### 2.2 不从随机卡组开始

卡组搜索以可靠人类卡组为中心，只允许受约束变异：

- 核心组件默认锁定；
- 连动组件作为一个 package 一起增删；
- 优先改变 flex/tech 槽；
- 先限制在距离种子卡组 4–10 张的邻域；
- 只有邻域搜索停滞后，才扩大搜索空间。

### 2.3 不只对一个最新对手训练

双方若只针对彼此最新版本，会出现脆弱的循环克制。评估时维护对手策略池：

- 人类基线；
- 历史最强版本；
- 当前最佳回应；
- 若干不同风格的稳健策略；
- 留出、不参与训练的测试策略。

## 3. 最短产出路径

### 里程碑 A：可用的专家基线

产出：

- 两个阵营各 2–5 套来源可靠的卡组；
- 每套卡组的核心、组件、功能牌和 flex 槽标注；
- 阵营/流派的行动特征权重；
- 起手、士气曲线、关键组合与天灾处理的人工规则；
- 抽牌概率和卡组稀释分析。

这一步还不需要完整强化学习，但已经能排除大量明显错误构筑。

### 里程碑 B：最小规则引擎

只实现第一组对抗需要的内容：

- 回合与阶段；
- 士气获得、消耗、休整和上限；
- 手牌、牌库、墓地、战场与位置；
- 军团登场、移动、攻击与死亡；
- 选定卡组实际使用到的效果；
- 天灾变量；
- 胜负与特殊胜利；
- 可复现的随机种子和完整行动日志。

规则引擎必须有两种模式：

- `strict`：发现未实现效果立即失败，禁止静默忽略；
- `research`：允许明确标注的近似效果，但报告中必须显示近似项。

### 里程碑 C：非随机策略与局面搜索

基线策略按以下顺序选动作：

1. 是否能立即获胜；
2. 是否必须阻止对手下一步获胜；
3. 是否违反生命、士气、手牌或天灾阈值；
4. 依据融合策略进行行动评分；
5. 对前 K 个动作做有限深度搜索；
6. 对隐藏信息从合理后验分布采样，而不是假设知道对手手牌。

首版建议使用：

- deterministic beam search；
- information-set rollout；
- transposition cache；
- action abstraction；
- endgame exact search（当剩余动作很少时）。

### 里程碑 D：卡组搜索

每个候选卡组经过分层筛选：

```text
便宜筛选
→ 中等样本复赛
→ 大样本决赛
→ 留出随机种子验证
→ 人工复盘代表性胜负局
```

使用 successive halving，快速淘汰明显较差方案。每组对局：

- 使用同一批随机种子比较候选与基线；
- 交换先后手；
- 按天灾场景分层；
- 不保存所有回放，只保存代表性、异常和最接近胜负边界的对局。

### 里程碑 E：强化学习升级

规则引擎和专家基线稳定后，再按顺序加入：

1. **行为克隆**：学习真人/搜索产生的好动作；
2. **策略残差**：网络只预测对专家评分的修正值；
3. **搜索蒸馏**：让快速网络模仿慢速搜索；
4. **群体自对弈**：面对历史策略池训练最佳回应；
5. **不完全信息算法**：按实际状态空间决定是否使用 Deep CFR / NFSP / PSRO 类方法。

不建议第一步就上大型 Deep CFR，因为它无法弥补规则错误和差的训练分布。

## 4. 人类强策略的采集与融合

每个来源记录：

- 来源 URL、作者、发布时间；
- 游戏和卡牌版本；
- 阵营、主宰、流派与对局；
- 完整卡组或可确认的卡牌；
- 对局数量和胜率（若有）；
- 起手换牌、关键回合、操作顺序；
- 该策略依赖的前提；
- 是否存在明显剪辑、娱乐构筑或单局幸存者偏差；
- 可信度与可复现性。

来源分层：

| 层级 | 示例 | 主要用途 |
|---|---|---|
| S | 当前版本官方规则/勘误/卡文 | 规则真值 |
| A | 多局比赛、稳定高胜率玩家、完整构筑与回放 | 强策略与卡组种子 |
| B | 设计者解说、完整单局、社区高质量攻略 | 战术假设与组合候选 |
| C | 单局片段、娱乐卡组、无版本信息分享 | 只生成待验证假设 |

官方机制说明权威地描述“卡如何工作”，但不自动证明某个构筑强；这两类证据必须分开。

## 5. 策略融合方式

不是把所有攻略机械平均，而是构建 mixture-of-experts：

```text
开局专家
中期资源专家
斩杀专家
防守专家
天灾专家
具体对局专家
```

状态门控器依据：

- 回合与士气；
- 双方生命/胜利进度；
- 手牌与资源；
- 场面威胁；
- 已知卡牌和对手流派后验；
- 当前天灾和潜在天灾。

当人类来源互相冲突时：

1. 优先当前版本；
2. 优先多局而非单局；
3. 优先完整对局而非剪辑；
4. 区分特定对局与泛用策略；
5. 将分歧保留为多个专家，不强行平均；
6. 用对局模拟决定门控条件。

## 6. 卡组优化变量

外层优化变量包括：

- 卡组总张数 40–50；
- 每张牌数量；
- 核心 package 是否存在；
- 通用卡数量与种类；
- 费用曲线；
- 抽牌/检索密度；
- 解场、保护、恢复和天灾保险；
- 针对牌与泛用牌比例。

约束包括：

- 阵营和同名卡规则；
- 必须能够执行主要获胜路线；
- 核心牌在目标回合前的到手概率下限；
- 死手率和士气浪费上限；
- 对训练外对手的泛化下限。

## 7. 评估指标

不只看总胜率：

- 总体胜率与 95% 置信区间；
- 先手/后手胜率；
- 对每类对手的胜率；
- 留出对手和留出随机种子胜率；
- 平均士气浪费、浪费至少 1 点的回合比例；
- 死手率和无有效动作率；
- 核心卡/组合在目标回合前到手率；
- 天灾分层胜率；
- 最差 10% 随机情景表现；
- 单卡消融和替换收益；
- 策略被新最佳回应击穿的程度。

## 8. 工程架构

```text
cards/rules JSON
      ↓
reference Python engine ──→ deterministic replay tests
      ↓
legal action generator
      ↓
expert safety policy + fused policy
      ↓
beam / rollout search
      ↓
deck optimizer + opponent population
      ↓
evaluation datasets
      ↓
GitHub Pages report
```

先使用可读的 Python 参考引擎加快规则实现。完成基准测试后，只把真正的热点迁移到 C++/Rust 扩展；不要为了理论性能延迟第一版可用结果。

## 9. MacBook Air M5 的默认运行方式

- 默认本地训练和模拟；
- 使用进程级并行跑独立对局；
- 设置 checkpoint 和可恢复任务；
- 控制 worker 数，避免无风扇机器长期极限降频；
- PyTorch 仅在后期通过 MPS 训练小型策略/价值网络；
- 训练结果保存为 JSON/Parquet，网页只负责展示。

云服务器后端保持同一实验接口，但不是第一阶段依赖。

## 10. GitHub Actions 与 Pages

GitHub Actions 只负责：

- 运行单元测试和规则回放测试；
- 校验卡牌/策略 JSON；
- 构建静态网页；
- 发布 GitHub Pages。

大量训练不放在托管 Actions 中。训练在本地或服务器运行，结果提交到 `results/` 后触发网页更新。

## 11. 首轮需要的输入

进入真实配卡前，需要：

1. 你们实际使用的规则版本和房规；
2. 第一组两个阵营与主宰；
3. 这两个阵营的完整卡牌数据或清晰照片；
4. 现有卡组、牌库码或你们常用构筑；
5. 至少若干完整对局记录，最好包含每步行动和结果；
6. 天灾卡和触发规则；
7. 先后手、初始手牌、换牌和士气规则的确认。

在这些数据不足时，系统可以提供概率与架构结论，但不会伪造具体最优卡表。
